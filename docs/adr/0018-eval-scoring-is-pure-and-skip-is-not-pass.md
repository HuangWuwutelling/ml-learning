# ADR-0018 · 评测判定逻辑做成纯函数，跳过不等于通过

- 状态: accepted
- 登记日期: 2026-11-03
- 决策日期: 2026-11-03

## 约束

QMS 项目的评测脚本 `eval/run_eval.py` 一直有两个指标没测过真东西（2026-11-03 修）：

- `tools_30`：另起一个 LLM 去「猜」该调哪些工具，只要模型回了非空字符串就算对，
  **从来没跟 `expected_tools` 比过**，所以它不可能失败。
- `no_tool_8`：用「回复长度 < 100」当「没调工具」的代理。调了工具回一段长文照样算过，
  没调工具但回得长的反而算错。

两个都写在 README 的评测表里，标着 SKIPPED，看起来像"等配 key 就能出分"，
实际上是两个不可能失败的指标。

同时还有三个现实约束：

1. **跑评测的机器环境不齐**：有的有 DeepSeek key 有的没有；
   NumPy 2.x 与 chromadb 0.5.5 不兼容（`np.float_` 被删），整条 `rag_20` 直接 import 失败。
2. **本机没有真 key**，不可能每次改判定逻辑都调真模型验证一遍。
3. **「没测出来」和「没达标」是两件事**，但两个都写成了 SKIPPED / 0 分，
   看表的人分不出"这个数字还没存在"和"这个数字很差"。

## 裁定

**判定口径抽成纯函数，指标只认真轨迹，跳过单列一档。**

- 判定逻辑放 `eval/scoring.py`：不 import Django / LangChain / 向量库，不碰网络。
  `run_eval.py` 从这里 import，「口径」和「跑分的脚本」是同一份定义。
  配套 `tests/test_eval_scoring.py`，在没有 key 的机器上就能验证口径本身没写错。
- 工具类指标必须读真轨迹：实际调用的工具从 `AIMessage.tool_calls` 上读
  （`agent/graph.py` 新增 `run_with_trace()` 回报调用序列）。
  **不许用回复长度、回复非空这类代理信号当"调没调工具"。**
- 退出码三态：
  - `0` = 4 个指标都跑到，且全部达标
  - `1` = 有指标跑到，但低于目标
  - `2` = 有指标没跑到（跳过）。数字没测出来，不算失败，**也不能当通过**。
- 整条指标一条都没跑起来 = **跳过**，不是 0 分（避免把"没配 key"说成"agent 全错"）。
- README 的评测表必须区分「数字」和「没测出来」，跳过不写数字。

## 后果

- 判定逻辑的 bug 在没有 key 的机器上也能被单测抓到，改口径不用每次烧 API 额度。
- 跳过不再伪装成通过：看退出码就知道这次跑有没有把数字测出来。
- **仍然测不了"智能"**：单测验的是口径，模型答得好不好要真跑、真 key。
  `tools_30` / `no_tool_8` 的真实数字到现在还没测出来（占位符 key），
  README 里写的是"没测出来"，不是数字。
- 代价是评测脚本多了一层：`eval/scoring.py` 与 `eval/run_eval.py` 两处都要改。
  口径定义只有一份，改的时候只改 `scoring.py`。
