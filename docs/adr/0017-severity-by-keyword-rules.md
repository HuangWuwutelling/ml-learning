# ADR-0017 · 严重度判定走关键词规则，不调 LLM

- 状态: accepted
- 登记日期: 2026-11-03
- 决策日期: 2026-11-03

## 约束

QMS 助手里 `assess_severity` 给客户投诉定严重度（high / medium / low），
下游 `draft_capa` 直接拿这个结论起草 CAPA。四个要求：

1. **要能解释**：质量经理得知道凭什么判成 high，不能只有一个「模型觉得」。
2. **要能离线复现**：评测集 `severity_25` 是四个指标里唯一不花钱的一个，
   判定方式一旦依赖 LLM，这个指标就只能在有 API key 的机器上跑。
3. **判定不能被数据状态带偏**：召回索引是可选产物（`scripts/seed_chroma_recall.py` 灌，
   `knowledge/chroma_db/` 是 gitignored 的），灌没灌不该改变同一句话的严重度。
4. **覆盖面窄是已知代价**：关键词表只有 7 个高危词 + 5 个中危词，
   判不了「虽然没写高危词但后果严重」的投诉。

原先的实现把 Chroma 查询放在关键词判定之前：查不到相似案例就直接返回 `medium`，
于是「灌了召回历史」和「没灌」的机器跑出两个不同的指标值。

## 裁定

**严重度由 `agent/tools.py` 的关键词表判定，不调 LLM；
判定与召回索引彻底解耦。**

- 先按关键词定 `severity` 与 `confidence`，再去查相似召回；
  查索引这一段包在 try/except 里，索引缺失或损坏只让 `similar_cases` 为空，
  不改判定结果，也不让工具报错。
- `severity_25` 这个指标的定位写死：**关键词规则表的回归测试，不是分类能力评测**。
  数据集标签与规则表同源，改了关键词表而没同步改数据集，这个指标就会掉分——
  这是它的设计意图。
- README 的评测表与评测结果 JSON 的 `scoring` 字段必须带上这句话，
  不许把 25/25 说成"分类准确率 100%"。

## 后果

- 判定可逐条追溯到触发的关键词，`similar_cases` 只作人工复核参考，不参与判定。
- 指标能在没有 key、没有向量库的机器上复现，也是一条真正的回归护栏。
- **100% 这个数字不能当"分类准不准"讲**。要谈分类能力，得换一批与规则表无关的
  人工标注数据；现有 `severity_25` 做不到这件事，也不假装做得到。
- 关键词表的维护成本转嫁到了数据集上：改规则就要同步改 `severity_25.jsonl`，
  两者不一致时以「哪边是错的」为准，不是以「指标别掉」为准。
