# ADR-0026 · 求职项目按岗位族能力矩阵设计，不为单份 JD 定制

- 状态: accepted
- 登记日期: 2026-11-10
- 决策日期: 2026-11-10

## 约束

求职目标是一份具体 JD（2026-11-03 更新）。讨论新项目时的第一版设计，是把自评出来的六个
红格逐条对着这份 JD 的六条职责去补，每一条红格对应一条 JD 职责。

这样做有三个问题：

1. **单份 JD 会变**。该岗位在招 1 人，用人部门换人时描述会改，半年后口径不一样。
2. **单份 JD 里有特色条款**。例如「AI 资产整理与治理：元数据 / Owner / Reviewer / 版本 /
   下线说明」，这是内部赋能岗的特色要求，绝大多数 AI 应用工程师岗位不这么要求。照着做，
   投入落在一个窄口径上。
3. **照抄 JD 会把对方的组织分工当成通用技术要求**。「跟嵌入式、硬件、测试团队 co-create」
   「由领域专家签字批准」这类是该团队的工作方式，不是这一岗位族的技术要求。

反过来，脱离具体 JD 只抽象出能力矩阵，也会做出「什么都沾一点」的通用 demo，没有一个
地方能被追问到底。

## 裁定

**求职项目按「岗位族通用能力矩阵」设计，具体 JD 只作矩阵的一个实例来核对，不作规格来照抄。**

矩阵分四块：**A AI 能力本体** / **B 工程与交付** / **C 落地与协作** / **D 通用素质**。
每项写成可观察的判据，不写成「了解 xxx」。

流程固定四步：

1. **建矩阵**：按岗位族（不是按公司）拆能力项，逐项写判据。
2. **自评**：对自己的现状逐格判红（真缺口）/ 黄（部分）/ 绿（已有）。
3. **新项目按红格设计**，且必须域中立——换公司、换行业仍然成立。
4. **具体 JD 只用来核对矩阵有没有漏项**，不用来决定做什么。

配套两条：

- **域中立优先于域对口**。项目避开单一行业标签，是为了让矩阵里每一格都能被追问；
  域对口的收益留给面试时讲行业理解，不写进项目本身。
- **特色条款不进设计主线，只作可选项**。像「AI 资产治理台账」这类，按一般工程惯例该有就补，
  不作为项目主线，也不因为某份 JD 提到了就升级成必做项。

## 后果

- 新项目立项先交一份「矩阵 + 自评」，写进设计稿第一节；设计稿不出现「针对某岗位」。
- 简历上写项目时同样不写「为某岗位设计」，写做了什么、谁用了、证据是什么。
- 已有三个主项目不受这条影响。它们是历史沉淀，不倒推改造。
- 具体 JD 的条款变化不再触发返工；矩阵变了才触发。
- 领域知识怎么处理，按这条裁定：写进需求场景与判据，不写进项目定位。域中立不等于没有
  场景，场景只是用来说明「谁在什么约束下用它」，不是项目的品牌标签。
